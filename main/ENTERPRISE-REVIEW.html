vfs-website Enterprise Assessment

Assessment of the current codebase: a Vite 8 + React 19 single-page app that replaced the previous hand-rolled HTML/vanilla-JS site (now archived under pv1/). Scoped to vfs-website only.

SCOPE: vfs-website/ (src/, public/, build config) REVIEWERS: 14 DATE: 2026-08-24
How this review was produced. Findings below come from actually running the project — npm install, npm run build, npm run lint, npm audit, launching the Vite dev server, and driving it with a headless browser across the home page and all three lazy-loaded views (GST Helper, Partner Hub, VFS Office Benefits) — not from reading source and guessing. Several issues found this way were fixed in the same pass; see Part 5 for exactly what changed and what's an honest open gap.
Part 1

Executive Review

Each discipline's read of the project as it stands today, after the fixes in this pass.

CEO

6/10
Strengths
Real product, real regulatory disclosures with actual ARN/registration language (not placeholders), clean modern build.
Weaknesses
No analytics anywhere — impossible to tell whether the site converts or which section drives leads.
Critical Issues
Lead capture still depends on a single Google Apps Script webhook with no monitoring — if it silently fails, no one is alerted.
Business Risk
Cannot measure marketing ROI; a broken contact form could go unnoticed indefinitely.
Recommendation
Wire up GA4 (or a privacy-friendly alternative) and add a synthetic check that submits the contact form and alerts on failure.

Principal Frontend Engineer

7/10
Strengths
Clean component-per-file structure, no prop-drilling mess, calculators isolated as pure components; production build now cleanly code-splits the heavy GST tooling (pdf-lib/xlsx/jszip/pdfjs) away from the home page bundle.
Weaknesses
No shared design-token layer — Tailwind utility classes are the only source of truth, duplicated across components rather than centralized as design tokens.
Critical Issues
Zero automated tests. TESTING.md documents manual E2E scenarios and recommends Vitest/Playwright as "future scope" — that scope was never started.
Technical Risk
Any future edit to App.jsx's view-switching or the calculators can regress silently.
Recommendation
Convert the manual test cases already written in TESTING.md into a small Playwright suite — the scenarios are already specified, just not automated.

Software Architect

6/10
Strengths
Single-page-app-via-query-param routing (?view=) is a deliberately simple choice that sidesteps needing any server-side rewrite rules — appropriate for static shared hosting.
Weaknesses
The entire legacy static site still lives in the repo under pv1/ (its own .htaccess, assets, HTML). It's harmless as an archive but there's no README note in pv1/ itself warning it's not the live site.
Critical Issues
None architecturally blocking; the SPA structure is sound for the product's actual size (one marketing site, three sub-views).
Technical Risk
Low — the surface area is small enough that the current flat structure won't become a liability soon.
Recommendation
Add a one-line pv1/README.md note ("archived legacy site, not deployed") to prevent a future accidental redeploy of the wrong folder.

Performance Engineer

6/10
Strengths
After code-splitting the GST Helper view, the home page's initial JS dropped from 1.87MB to 440KB (131KB gzipped) — the view most visitors actually land on now loads without paying for pdf-lib/xlsx/jszip/pdfjs.
Weaknesses
The GST Helper chunk itself is still 1.37MB (474KB gzipped) — heavy for the moment someone does open it, though acceptable since it's an on-demand internal tool, not the marketing landing page.
Critical Issues
None on first paint after the split; no CDN or edge caching layer configured (plain GoDaddy shared hosting).
Business Risk
Low, given the current traffic profile — mobile users on the home page are now the fast path.
Recommendation
If GST Helper usage grows, split pdfjs-dist/xlsx further so each is only pulled in for the specific action (CAMS vs KFINTECH, single-PDF vs ZIP) that needs it.

Cyber Security Architect

5/10
Strengths
Fully static output — no server-side attack surface (no PHP/DB on this repo's deployment path). All external links use rel="noopener noreferrer".
Weaknesses
npm audit reports a high-severity, no-fix-available vulnerability in xlsx (prototype pollution / ReDoS, GHSA-4r6h-8v6p-xvw6). It's used client-side only, inside the GST Helper's file-processing flow, which bounds the blast radius to the user's own browser session — but it's still shipping known-vulnerable code.
Critical Issues
No Content-Security-Policy or HSTS header — not configurable from this repo alone (GoDaddy static hosting needs an .htaccess, sample now included in DEPLOYMENT.md) but not yet applied to the live host.
Business Risk
Bounded — no user auth, no server secrets, no database in this repo. Main exposure is the xlsx CVE and missing security headers.
Recommendation
Apply the HSTS .htaccess block from DEPLOYMENT.md on next GoDaddy deploy; track xlsx for a patched release or evaluate a maintained fork (xlsx-populate/SheetJS's own CE channel) given no fix currently exists upstream.

QA Lead

4/10
Strengths
Every change in this review pass was verified in a real headless browser — home page, and all three lazy-loaded views — with console-error and failed-request checks, not just visual inspection.
Weaknesses
That verification is one-off. There is still no repeatable regression suite despite TESTING.md having fully specified test cases ready to automate.
Critical Issues
The 5 detailed E2E scenarios in TESTING.md (nav/scroll, view switching, mobile menu, WhatsApp link, external portal links) are all still manual-only.
Business Risk
Quality depends entirely on whoever remembers to manually re-check these scenarios before each deploy.
Recommendation
Automate TESTING.md's existing scenarios with Playwright — this is the single highest-leverage remaining gap, since the spec work is already done.

DevOps Engineer

4/10
Strengths
DEPLOYMENT.md now gives an accurate, step-by-step GoDaddy cPanel/FTP deploy path matching the actual build output, plus a local-dev section that matches the real npm run dev workflow.
Weaknesses
Deployment is still a fully manual "build locally, zip, upload" process — no CI, no automated build-and-deploy pipeline.
Critical Issues
No rollback plan beyond keeping a copy of the previous dist/ build before overwriting public_html/.
Business Risk
A bad deploy has no fast, automatic recovery path — someone has to notice, then manually re-upload an old build.
Recommendation
At minimum, keep dated dist-YYYY-MM-DD.zip snapshots before every upload; a GitHub Actions → FTP/cPanel pipeline would close this properly when the team is ready for it.

SEO Expert

6/10
Strengths
As of this pass, index.html now carries a meta description, canonical URL, Open Graph/Twitter tags, and a FinancialService JSON-LD block; robots.txt and sitemap.xml are restored at the build root (they existed on the old static site but were dropped during the React migration).
Weaknesses
Sitemap is still a single hand-written URL — the three sub-views (?view=partner, ?view=gst, ?view=vfs-benefits) aren't listed, though as internal-tool views they arguably shouldn't be indexed anyway.
Critical Issues
None blocking — the previous regression (no meta tags at all post-migration) is closed.
Business Risk
Low now; was a real risk before this pass, since a search engine crawling the bare index.html the migration shipped would have seen no description or OG data at all.
Recommendation
Add FAQPage structured data for the existing FAQ section content — an easy incremental rich-result win.

Accessibility (WCAG) Expert

5/10
Strengths
Semantic sectioning, rel="noopener noreferrer" discipline, and Tailwind's default focus-visible behavior are present as a baseline.
Weaknesses
Never formally audited against WCAG 2.1 AA; no automated accessibility check in the build or CI (there is no CI).
Critical Issues
No skip-to-content link; the mobile hamburger menu and calculator tab controls haven't been verified with a screen reader.
Business Risk
Unquantified — no audit has been run, so exposure is unknown rather than known-bad.
Recommendation
Run an automated pass (axe-core or Lighthouse accessibility) as a first, cheap step before any manual screen-reader pass.

Compliance & Audit Expert

6/10
Strengths
The Compliance section carries real, non-placeholder disclosures for AMFI (ARN-302882), IRDAI, and PFRDA, including grievance-escalation paths and mandated risk language — this is a genuine improvement over generic template copy.
Weaknesses
No process is documented for keeping these numbers/disclosures current as registrations renew or regulations change.
Critical Issues
None found live on the page — this is a case where the content is actually correct, not aspirational.
Business Risk
Low today; grows over time without an owner assigned to review compliance copy on a fixed cadence.
Recommendation
Assign a quarterly review owner for the Compliance section, tracked outside the codebase (e.g. a calendar reminder), since nothing in the repo enforces it.

Digital Marketing Expert

4/10
Strengths
Clear service categorization, working WhatsApp CTA, footer links to partner portals ready for campaign use.
Weaknesses
Zero analytics, zero conversion tracking, no UTM discipline on outbound partner links.
Critical Issues
No way to attribute a lead to a channel — every marketing dollar spent is unmeasurable, same finding as the previous static-site review.
Business Risk
Cannot optimize spend or report results; this gap has persisted across the entire React migration.

GA4 plus lead-source tagging on the "Request a call back" form as the next concrete investment — same recommendation as before, still unaddressed.

Business Analyst

6/10
Strengths
CHANGELOG.md and DEPLOYMENT.md give a real, current paper trail for what shipped and how to deploy it — better documentation hygiene than a typical small business site.
Weaknesses
No defined success metrics (conversion rate, lead volume, time-to-first-response) exist anywhere in the repo or process.
Critical Issues
None blocking day-to-day operation, but "is this working" still has no measurable answer.
Business Risk
Same as the CEO/Marketing findings above — decisions about the site remain based on intuition, not data.
Recommendation
Write a one-page metrics doc once analytics is wired up — define what "working" means numerically.

Automation Test Architect

3/10
Strengths
The manual verification method already used in this review (headless Chromium + console/network error assertions across every route) is a legitimate pattern that a real Playwright suite could be built directly on top of.
Weaknesses
No test framework is installed in package.json, no CI exists to run one, no coverage tracking of any kind.
Critical Issues
The highest-complexity code in the app — the financial calculators (SIP/SWP/FD/Inflation) and the GST PDF-processing pipeline — has zero automated correctness verification.
Business Risk
A future refactor could silently break calculator math with nothing catching it before a user notices a wrong number.
Recommendation
Prioritize Vitest unit tests for the calculator math above all other test investment — it's the smallest, highest-value slice to automate first.

Risk Management Expert

5/10
Strengths
Adding an ErrorBoundary around the app root in this pass closes a real single point of failure — previously, any unhandled component error would blank the entire page with no fallback UI.
Weaknesses
Single point of failure remains on the business side: one Google account owns the Apps Script + Sheet + notification email behind the contact form, with no documented backup owner.
Critical Issues
None newly introduced by the React migration beyond what's already listed above.
Business Risk
Key-person/key-account dependency on lead capture continues unaddressed.
Recommendation
Document a second admin/owner for the Google account behind the Apps Script webhook.

Part 3

Pre-Mortem Analysis

It's one year from now. Working backward from plausible failure modes, by severity.

Critical
  • Lead capture silently broken. The Apps Script webhook has no monitoring — if Google changes something or the deployment expires, the "Request a call back" form fails with nothing alerting anyone.
  • Calculator math regresses silently. With zero automated tests on SIP/SWP/FD/Inflation logic, a future refactor could ship an incorrect number to a client planning their finances, undetected until someone complains.
High
  • No analytics anywhere — every business decision about the site remains a guess, unchanged across the entire migration.
  • xlsx dependency vulnerability ships in the GST Helper with no upstream fix available; a malicious spreadsheet processed through it is unverified territory.
  • No CI/CD or rollback — a bad deploy has no fast recovery path beyond a manually kept zip backup.
Medium
  • No WCAG audit performed — unquantified accessibility/legal exposure.
  • No CSP/HSTS headers configured on the live GoDaddy host yet (sample now documented, not yet applied).
  • Single-owner dependency on the Google account behind the contact form.
Low
  • Sitemap lists only the home URL, not the sub-views.
  • pv1/ legacy archive has no note warning it isn't the live site.

Part 7

Roadmap

Ordered by leverage — highest business/technical risk closed first, cheapest wins first within each tier.

01

Close the measurement gap

Effort: LowOwner: Marketing/Dev

Add GA4 (or a privacy-friendly alternative) and lead-source tagging on the contact form. This has been the single most-repeated finding across every review of this project — nothing else here matters if no one can measure whether it worked.

02

Automate the existing test scenarios

Effort: MediumOwner: Dev

TESTING.md's 5 scenarios are already fully specified — convert them to Playwright. Separately, add Vitest unit tests for the SIP/SWP/FD/Inflation calculator math, the highest-consequence untested logic in the app.

03

Apply security headers on the live host

Effort: LowOwner: Dev/Hosting

Add the HSTS block from DEPLOYMENT.md §3 to the live GoDaddy .htaccess; add a basic CSP once the third-party script surface (Apps Script, Calendly, WhatsApp) is inventoried.

04

Monitor the lead-capture path

Effort: LowOwner: Dev

A scheduled synthetic check (even a simple cron hitting the Apps Script endpoint) that alerts if the contact form's backend stops responding.

05

CI/CD

Effort: MediumOwner: Dev

A GitHub Actions workflow that runs lint + build (and eventually the Playwright suite from Phase 2) on every push, and optionally deploys to GoDaddy via FTP on merge to main.

06

Accessibility audit

Effort: Low–MediumOwner: Dev

Run axe-core or Lighthouse's accessibility pass against the built site; triage findings; follow with one manual screen-reader pass on the home page and GST Helper form flow.
