vfs-website Enterprise Assessment

A 24-discipline review board evaluation of the vfs-website project — the public marketing site (v1 + v2), the Partner Info and MFD/GST tooling modules, and the new backoffice authentication foundation. Scoped to vfs-website only; vemuri-group and vfsoffice are separate repositories and out of scope.

SCOPE: vfs-website/ REVIEWERS: 24 PARTS: 9
Addendum (post-review changes) — not a re-score. Since this review was written, two major rounds shipped: (1) a full 3-layer enterprise configuration architecture (secrets/.env+config.php, admin-editable settings table, system-level constants) with dedicated Database/SMTP/Payment/Security/Logging/Feature-Flags admin pages — see backoffice/docs/configuration-architecture.md and configuration-matrix.md; and (2) a broad bug-fix/UX round across calculators, AMC editing, the payment flow, and email — see backoffice/docs/release-notes.md's latest entry for the full list. Several items the scorecard/gap-analysis below flag as missing are now closed: HTTP security headers and IP-based rate limiting (already re-verified as resolved in security-review.md §8–9 independently of this review), and the configuration-management gap this document's Enterprise Architecture section discusses. The scores, gap analysis, and pre-mortem below are the original assessment and have deliberately not been re-run — a fair re-score needs a fresh audit pass, not a guess layered on top of an old one. The repo has also been restructured since this was written: the old v2/ nesting is gone, promoted to the repo root (see root README.md).
Second addendum (2026-08-08, production-deploy readiness) — also not a re-score. Ahead of a first production deployment of both vfs-website and vfsoffice, a further round closed most of what this review's Gap Analysis and Production Readiness Checklist (Part 7) flag under Security/Documentation:
  • Data-protection compliance: a public Privacy Policy and a Compliance & Regulatory Standing page (both in vfsoffice, linked from this site's footer and forms), consent capture enforced server-side at every personal-data collection point (including this site's "Request a call back" form), and a breach-response runbook with concrete containment/notification steps — see vfsoffice/docs/data-protection-security-compliance.md and breach-response-runbook.md.
  • Self-service account deletion (password re-check + typed confirmation + anonymize-in-place, not a hard delete) — closes the DPDP Act "erasure" data-principal right this review didn't originally assess.
  • vfsoffice's database baseline (01_schema.sql/02_seed_data.sql) was found to have drifted from its own migration history — 3 missing tables, 1 missing column, 3 missing seed rows — found by actually running the imports and diffing against a live database, not by reading file text. Fixed, verified, and a docs/feature-release-process.md written so it can't silently drift again. This directly addresses this review's Part 7 "Backup strategy"/"Disaster recovery plan" gaps' precondition: neither is meaningful if the schema you'd restore from isn't actually correct.
Still open, per this review's own checklist: Monitoring, Analytics, Error tracking beyond the existing email-alert mechanism, a formal backup/DR runbook (the schema is now trustworthy; a documented restore drill still is not), and CI/CD. None of those were in scope for this round.

Part 3

Pre-Mortem Analysis

It's one year from now. The project has failed. Working backward from that failure, by stakeholder and by severity.

By stakeholder

  • Customers: "I filled out the call-back form twice and never heard back." The Apps Script backend was never deployed, or the one-time email confirmation was never clicked, and nobody noticed for months because there was no monitoring on it.
  • Investors/Owners: Couldn't answer "how many leads did the website generate this quarter" — no analytics existed at any point, so spend could never be justified or optimized.
  • Employees/Advisors: Kept using WhatsApp and phone calls exclusively because the backoffice tools (partner hub, GST workflow) were never adopted — no training, no rollout plan, just a link in a footer.
  • Financial Advisors (external MFD network): Distrust set in when the AMC directory in Partner Info went stale — portal URLs changed, RM contacts moved on, and nobody owned keeping the hardcoded data current.
  • Developers (future): Onboarding took two weeks instead of two days because there was no README explaining why three folders (vemuri-group, vfs-website, vfsoffice) exist, which one is live, and which is legacy.
  • Auditors: Found the IRDAI/PFRDA placeholder numbers were still placeholders eighteen months after go-live, because nobody owned "keep compliance data current" as a job.
  • Search Engines: Indexed both v1 and v2 as duplicate homepages, split link equity between them, and neither ever ranked well for the target keywords.
  • Competitors: Out-ranked and out-converted VFS because their sites had analytics-driven iteration from day one, while this site's roadmap stayed guesswork.

Ranked risk register

Critical
  • Lead capture silently broken. The Apps Script deployment is a manual, one-person step with no monitoring — if it breaks, nothing alerts anyone.
  • No backup strategy for the MySQL database once the backoffice holds real user/audit records — a hosting incident means permanent data loss.
  • Compliance placeholders shipped live ([IRDAI no.], [PFRDA no.]) — direct regulatory exposure for a licensed distributor.
  • Backoffice auth code never executed before this review — security-critical code with zero runtime verification.
High
  • No analytics anywhere — every business decision about the site is a guess.
  • Two competing homepages (v1, v2) confuse both users and search engines.
  • No CI/CD or rollback — a bad deploy has no fast recovery path.
  • No automated tests — every future change risks silent regression.
  • Single-owner dependency on the Google account behind the contact form.
Medium
  • Vendor JS libraries (pdf-lib, xlsx, jszip) unpinned and unmonitored for CVEs.
  • 967KB logo image never compressed — real but bounded performance cost.
  • No WCAG audit performed — unquantified accessibility/legal exposure.
  • No CSP/HSTS headers configured.
  • Placeholder testimonials never replaced with real client voice.
Low
  • Sitemap is a single hand-written URL rather than generated.
  • No design-system documentation beyond the CSS itself.
  • Inline style="" attributes remain in a few v2 pages.

Part 5

Enterprise Architecture

Evolving the implementation without touching the navigation, workflow, or business logic already in place.

Project structure (target state)

vfs-website/
├── site/                    # now the repo root — public marketing site (this proposal predates the actual v2-to-root promotion, kept here as historical review content)
│   ├── index.html, partner-info.html, mfd-gst.html
│   └── assets/{css,js,images,vendor}/
├── backoffice/               # PHP + MySQL foundation (this review's newest layer)
│   ├── inc/                  # db, auth, audit, helpers, layout
│   ├── modules/               # future: amcs/, ekyc/, finplanner/, reports/ (ported incrementally)
│   └── database/schema.sql
├── shared/                   # NEW — single source of tokens.css/base.css/components.css,
│                              #        synced (not copy-pasted) into site/ and backoffice/
├── docs/
│   ├── ARCHITECTURE.md        # NEW — the one-page target state the Enterprise Architect review calls for
│   ├── ONBOARDING.md           # NEW
│   └── CHANGELOG.md            # NEW
└── .github/workflows/deploy.yml   # NEW — CI/CD, see Part 8

Reusable components

Keep the existing blueprint-card/button/badge vocabulary (already consistent across v2, partner-info, mfd-gst, and the new backoffice) as the canonical component set. Don't introduce a second system for backoffice's future feature modules — extend the same one.

CSS architecture

Current layering (tokens → base → components → page-specific) is correct and should be preserved exactly. The only structural change needed: move tokens.css/base.css/components.css to shared/ and reference them from both site/ and backoffice/, closing the copy-paste-drift risk the Software Architect review flagged — without a build step, this can be a simple deploy-time file copy documented in one script.

JavaScript architecture

Preserve the existing pattern: small, single-purpose modules (calculators.js, quiz.js, contact-form.js) loaded as plain script tags, no bundler. This is the right call for the hosting constraint and should not be "modernized" into a framework — that would be a regression, not an improvement, for this deployment target.

Logging, error handling, audit

Extend the backoffice's existing logAction() pattern (already correctly designed) to every future module rather than inventing a new logging approach per module. For the static marketing site, add a minimal client-side error reporter that posts JS exceptions to the same Apps Script endpoint already handling leads, tagged distinctly.

Monitoring & analytics

GA4 on the marketing site (event tracking on quiz completion, calculator use, form submit). A simple uptime check (e.g. a free-tier UptimeRobot ping against the homepage and the backoffice login page) — inexpensive, high-value, currently entirely absent.

Deployment / CI-CD-ready / environment config

Introduce a GitHub Actions workflow that runs the (new) test suite, then FTP/SFTP-deploys on merge to main — no change to the manual GoDaddy hosting target, just automation in front of it. Environment config already exists as a pattern (config.local_dev) — extend it with a proper .env-style split once a second environment (staging) exists.

Future API integration

The backoffice's flat PHP structure can grow an /api/ subfolder returning JSON for future needs (e.g. the marketing site querying live AUM figures) without disrupting the existing page-per-file pattern — additive, not a rewrite.

5. Production Folder Structure

See Part 5 — shared/ consolidation is the one structural change recommended; everything else is additive to what exists.

6–7. CSS & JavaScript Architecture

Preserve as-is: layered CSS (tokens→base→components→page), small single-purpose JS modules, no bundler, no framework. This is a deliberate strength, not a gap, for this hosting target.

8. Logging Strategy

Extend the backoffice's logAction() pattern everywhere; add a client-side JS error reporter on the marketing site posting to the same lead-capture backend, tagged as error events.

9. Audit Strategy

The audit_logs schema (user, action, entity, IP, timestamp) is correct and should become the standard every future module writes to — including the MFD tool and, eventually, a marketing-site content-change log.

10. Monitoring Strategy

Free-tier uptime monitor today; GA4 this month; Sentry-equivalent (or even just PHP error-log email alerts) before the backoffice holds real client data.

11. Security Strategy

Execute and verify the backoffice auth design that already exists; add CSP/HSTS; establish a vendor-dependency update cadence; extend audit coverage. The hard design work is done — this phase is verification and header configuration, not a redesign.

12. Deployment Strategy

Keep GoDaddy shared hosting as the target (confirmed, appropriate for scale); add CI in front of it (GitHub Actions → FTP), dated backup snapshots before every deploy, and a written rollback procedure.

13. Maintenance Strategy

Quarterly review of every numeric/regulatory claim on the site; a named owner for each external service dependency; a CHANGELOG kept current per deploy.

14. Future Roadmap

Port the remaining ~20 vfsoffice modules into the new PHP foundation incrementally, each wired into the same audit log from day one — not retrofitted later, learning from exactly the gap this review found in the MFD tool.

15. Final Recommendation

Do not redesign. The product, navigation, and business logic are sound and shouldn't change. Spend the next cycle entirely on operational maturity — deploy what's built, monitor what's deployed, back up what matters, and automate what's currently manual. That single shift moves this from a 5.4 to a genuinely production-ready platform without touching a single page of UI.
